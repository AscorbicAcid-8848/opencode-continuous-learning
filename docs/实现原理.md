# OpenCode 持续学习插件是怎样工作的

这是一套从 OpenCode 插件接口出发实现的持续学习机制。基础 Memory/Skill 仍由本地 TypeScript 实现；0.5.0 的会话检索、Journey、后台审批和 Provider 生命周期参考 Hermes Agent 的公开源码与文档，再按 OpenCode 的 hook、会话 API 和 TUI 能力改写。SQLite 使用 Bun 内置 `bun:sqlite`，Honcho 使用官方 `@honcho-ai/sdk`，Mem0 使用官方 REST API。所谓“学习”不是训练模型权重，而是持久化事实、会话索引和可重复执行的方法。

理解这份代码，最自然的顺序不是先背模块名，而是跟着一次会话往下走：OpenCode 启动时装入插件，新会话先取得旧知识，用户与 Agent 正常工作，任务结束后插件判断是否需要复盘，最后把新知识安全地写到磁盘。服务端入口在 [`src/plugin.ts`](../src/plugin.ts)，原生设置面板在 [`src/tui.ts`](../src/tui.ts)，基础存储与校验集中在 [`src/core.ts`](../src/core.ts)，FTS5、审批、Journey 和 Provider 位于 [`src/advanced.ts`](../src/advanced.ts)。

## 插件启动后先建立自己的边界

OpenCode 加载插件时会调用 `src/plugin.ts` 中的默认导出函数。入口先确定三类位置：插件配置放在 `~/.config/opencode/continuous-learning/config.json`，记忆和运行状态放在 `~/.local/share/opencode/continuous-learning`，Skill 则写入 OpenCode 原生的 `~/.config/opencode/skills`。随后它读取配置并创建 `LearningStore`，不会修改用户原有的 `opencode.jsonc`。

默认配置把总开关 `enabled` 和记忆上下文开关 `memoryContextEnabled` 都设为开启，并把自动复盘间隔设为 10 个用户回合或 15 次工具调用。这两个复盘条件彼此独立，任何一个达到阈值都可以触发复盘。配置解析不是把 JSON 原样相信下来，而是由 `src/core.ts` 中的 `normalizeConfig()` 检查类型并限制取值范围。例如并行复盘最多允许 8 个，实际默认只开 2 个，避免多个会话同时空闲时突然发起大量模型请求。

插件还在配置钩子中注册了一个隐藏的 `continuous-learning-review` Agent。这个 Agent 不是给用户选择的工作 Agent，而是自动复盘的隔离执行环境。它拒绝编辑、终端、网络抓取和外部目录权限，并只声明三个学习工具。这样，正常工作仍由用户当前的 Agent 完成，后台复盘只能整理已经发生过的会话。

## 新会话如何取得以前学到的内容

每次模型准备生成回答时，OpenCode 会调用 `experimental.chat.system.transform`。只有 `enabled` 和 `memoryContextEnabled` 同时开启，插件才会把长期记忆、用户画像和 Skill 的名称与描述追加到系统提示。真正拼装这段文字的是 `src/core.ts` 的 `buildSystemSnapshot()`；关闭记忆上下文不会停止后台学习或删除数据。

这里故意只放 Skill 索引，不把每个 `SKILL.md` 的全文全部塞进上下文。模型发现某个 Skill 与当前任务有关时，再调用 `learning_skill view` 读取全文。这样 Skill 数量增加以后，系统提示不会按全部正文的体积不断膨胀。

同一个会话第一次生成这段提示后，结果会缓存在 `systemSnapshots` 中。之后即使 Agent 新增了一条 Memory，当前会话已经使用过的提示前缀也不会突然改变。新知识会在新会话中出现；如果 OpenCode 对当前会话做了上下文压缩，插件会清除旧快照，在新的提示边界重新读取磁盘。这让会话上下文保持可预测，也避免一次写入让前面已经缓存的提示失效。

总开关关闭时，系统提示钩子不会追加这段快照，空闲事件不会读取会话或启动复盘，Memory 与 Skill 工具也会拒绝操作。用户通过 `/learning-settings` 面板更新总开关；服务端会自动重载配置并清除快照缓存。底层控制工具和只读状态工具始终保留，确保模式关闭后仍能重新开启。

OpenCode 的服务端插件与 TUI 插件是两个独立入口，不能由同一个模块同时导出。因此安装包保留原来的服务端入口，同时把 `src/tui.ts` 作为独立 TUI 插件登记到 `tui.json`。它使用 OpenCode 原生 `DialogSelect`、`DialogPrompt` 和 `DialogConfirm` 组成 `/learning-settings` 面板，不经过模型。面板写配置时复用 `src/core.ts` 的严格校验与原子写入；服务端在下一次系统提示、空闲事件或学习工具执行前重新读取配置，并原地更新 `LearningStore` 持有的同一配置对象，所以所有限制也会随之生效。

## `/learn` 只是主动学习入口，不是另一套引擎

[`commands/learn.md`](../commands/learn.md) 是一个标准 OpenCode 命令模板。用户输入 `/learn 某个主题` 后，`$ARGUMENTS` 会被替换成主题，当前主 Agent 仍然使用它原本拥有的代码检索、文件、终端或网页工具完成调查。命令要求它先核实资料，再用 `learning_skill list` 或 `view` 查重，最后调用 `create` 或 `update` 写入一个可复用的 Skill。

因为这次学习是用户明确发起的，写入前会经过 OpenCode 权限确认，生成的 Skill 被标记为用户所有。另一个命令 [`commands/learn-review.md`](../commands/learn-review.md) 用于立即复盘当前会话；它同样在前台运行，所以结果仍由用户控制。两条命令只是给当前 Agent 一段明确的工作说明，真正落盘仍统一经过插件工具和存储层。

## 工具表面把“想学”和“想回忆”变成可控操作

`learning_memory` 管理三种作用域：全局 `MEMORY.md` 保存跨项目环境事实或长期约定，`USER.md` 保存用户身份和偏好，`projects/<项目名>-<路径哈希>/MEMORY.md` 保存当前项目的架构、命令、约束和持久决策。项目根优先采用包含当前目录且不是文件系统根的 OpenCode worktree，否则使用启动目录；路径哈希让同名项目保持隔离。工具支持查看、新增、精确替换和删除。比如“这台机器执行 PowerShell 脚本受限”适合放进全局 Memory，“这个仓库使用 Maven Wrapper”适合放进项目 Memory，而“刚才测试端口是 42317”只是临时状态，不应保存。

`learning_skill` 负责列出、读取、创建、更新和归档程序性知识。归档删除会把目录移动到 `.continuous-learning-archive`，不会直接递归擦除；后台还要通过可信 provenance 和 `absorbed_into` 双重约束。

`learning_status` 不负责写知识，只返回当前配置、存储路径、Memory 数量、Skill 数量以及各会话的复盘检查点。它主要用于排查“为什么还没有自动复盘”或“学习结果写到哪里了”。

`learning_mode` 是保留的内部总开关控制工具，支持 `status`、`on`、`off`，在模式关闭时仍可用；用户侧不再注册对应 Slash 命令，统一通过设置面板操作。后台复盘 Agent 没有使用它的权限。

`session_search` 在第一次使用时调用 OpenCode 的 `session.list` 与 `session.messages` 补建当前项目旧会话，之后由 `session.idle` 增量写入全局 SQLite。FTS5 命中返回开头、命中窗口和结尾，中文或特殊查询在 FTS 无结果时回退到大小写无关的子串检索。`learning_pending` 管理持久审批记录，`learning_journey` 返回时间线或关系图，`learning_external_memory` 只暴露 Provider 状态和搜索，不回显凭据。

## 后台写入为什么能真正暂停

`backgroundWriteApproval` 开启时，Memory/Skill 工具在识别到 `automaticSessions` 中的 reviewer 会话后，不调用 `LearningStore`，而是把完整、尚未执行的操作写成独立 pending JSON。批准时 `applyPendingRecord()` 为记录中的项目根重新创建 `LearningStore`，再走同一套内容扫描、唯一匹配、容量、所有权和符号链接检查。队列记录只有应用成功才移入 approved 历史；失败会恢复成 pending，因此不会出现“界面显示已批准但实际没写”的状态。

## 会话搜索、Journey 与外部 Provider 的边界

会话全文索引保存在 WAL 模式 SQLite，`sessions` 保存元数据，`messages` 保存正文，外部内容 FTS5 表由触发器同步。OpenCode 1.18 的列表接口按当前项目实例工作，因此真正的跨项目效果来自所有项目插件实例共同写入同一个全局数据库；从未打开过的其他项目不能被当前实例主动枚举。

Journey 记录最多 5,000 个学习事件。图谱把当前 Memory 和 Skill 变成稳定 ID 节点，用中英文词元重叠连接 `related_to`，再用事件时间连接 `learned_after`。它复现 Hermes 现有 Journey 的“让学习可见”目标，不冒充仍处于提案阶段的向量混合知识图谱。

外部 Provider 只有用户把枚举从 `builtin` 切到 `mem0` 或 `honcho` 后才工作。普通对话的 `chat.message` 捕获当前用户文本，system transform 发起带超时的召回并明确把结果标为不可信历史上下文；`session.idle` 把最后一组用户/助手文本同步出去。网络失败只记录警告，不影响本地学习链路。

## 自动学习从 `session.idle` 开始

OpenCode 在一轮回答结束后会发出 `session.idle` 事件。这个事件表示本轮暂时空闲，并不表示用户关闭了会话，所以插件不能每次收到事件都启动复盘。`src/plugin.ts` 的 `maybeAutoReview()` 会先检查自动学习是否开启、这个会话是否已经在复盘、全局并发是否达到上限，然后读取完整会话消息。

消息进入复盘前会经过 `extractTranscript()` 清洗。代码只保留用户和助手的普通文本，并记录已经完成或失败的工具调用；推理片段、合成消息和被忽略的文本不会进入学习材料。`countTranscript()` 分别统计用户回合数与工具调用数，`isReviewDue()` 再把它们与上一次成功复盘的检查点比较。失败的复盘不会推进成功检查点，而是记录错误并进入冷却期，下一次不会立刻重复消耗模型。

达到阈值后，插件不会把“请复盘”追加到用户原会话。它调用 OpenCode SDK 创建一个带 `parentID` 的子会话，把经过长度限制的会话副本交给隐藏复盘 Agent。随后它读取 OpenCode 当前解析到的工具列表，全部关闭，再只打开 `learning_memory`、`learning_skill` 和 `learning_status`。复盘提示还会说明本次究竟是 Memory 条件到期、Skill 条件到期，还是两者都到期；工具执行层会再次检查这个条件，不能只靠模型自觉遵守。

子会话返回后，代码不仅检查 SDK 请求是否成功，还检查 AssistantMessage 中是否带有模型错误以及是否真正完成。只有确认成功，才会把新的回合数、工具数和最后消息 ID 写进检查点。最后插件删除这个内部子会话，原会话里不会出现复盘提示、复盘推理或内部回答。

## 主动学习和自动学习共用工具，但所有权不同

前台 `/learn` 可以调查外部资料，结果属于用户；后台自动学习只能阅读已经完成的会话，创建结果属于自动管理范围。这一区别不是写在提示里的一句约定，而是存储层实际执行的策略。

每个由插件创建的 Skill 都有一份独立 provenance JSON，记录 `owner`、`autoManaged`、来源会话、时间以及 `SKILL.md` 内容的 SHA-256。后台更新 Skill 时，`updateSkill()` 会重新计算当前文件的哈希。只有 sidecar 结构合法、所有者确实是 `agent`、`autoManaged` 为布尔值 `true`，并且当前文件仍与上次插件写入的哈希一致，自动更新才被允许。

这意味着用户只要手工修改过自动生成的 `SKILL.md`，哈希就会变化，后台会立即把它当成用户内容而拒绝覆盖。用户在前台使用工具更新一次，也会把所有权降为 `user`。旧的 sidecar、伪造的字符串布尔值或删除后重新建立的同名目录，都不能让后台取得修改权。

## 文件为什么不直接 `writeFile` 覆盖

`src/core.ts` 的 `atomicWriteText()` 先在目标目录写临时文件，调用 `sync()` 刷新文件内容，再用重命名替换目标；Windows 遇到杀毒软件或索引器短暂占用文件时会做有限重试。多个 OpenCode 进程同时写入时，`withStorageLock()` 使用带随机所有者标识的独占锁文件串行化操作。锁文件会记录所有者、PID、主机和创建时间；遇到已有锁时会校验 PID 与租约，确认持有者已退出后才安全回收陈旧锁（回收前会再次读取并核对所有者，避免误删另一个进程刚创建的新锁）。释放锁前同样核对所有者，不能因为一个过期操作误删另一个进程的新锁。

创建 Skill 比更新更谨慎。`createSkill()` 先用不可覆盖的方式创建整个 Skill 目录，只要同名目录已经存在就立即拒绝；`SKILL.md` 本身也使用 `wx` 独占创建。因此即使用户恰好同时建立同名 Skill，插件也不会用重命名把它覆盖掉。

Memory 文件也不会宽松解析后全量重写。`parseMemory()` 要求文件保持受管的标题、注释和单行条目格式；一旦发现人工加入的未知段落，后续增删改会报错并保留原文件，而不是只抽取 `- ` 开头的行后静默丢掉其他内容。持久内容在落盘前还会做 Unicode 规范化、提示注入特征和常见凭据格式扫描，容量也有上限。

## 当前版本实际验证到了哪里

核心测试位于 [`tests/core.test.ts`](../tests/core.test.ts)，高级能力测试位于 [`tests/advanced.test.ts`](../tests/advanced.test.ts)，插件编排测试位于 [`tests/plugin.test.ts`](../tests/plugin.test.ts)，设置面板测试位于 [`tests/tui.test.ts`](../tests/tui.test.ts)。除原有安全和复盘路径外，它们还验证 FTS5 四种读取形状、pending 批准/拒绝历史、后台暂存集成、Journey 关系边、Skill 可恢复归档和 Mem0 V3 请求结构。

安装后可用 `opencode debug config` 确认服务端插件、隐藏复盘 Agent 和工具；TUI 插件应注册 `/learning-settings`、`/learning-pending` 与 `/learning-journey`。本地测试不会请求真实 Mem0/Honcho 或调用模型；外部服务需要用户自行配置后做连通验证。
