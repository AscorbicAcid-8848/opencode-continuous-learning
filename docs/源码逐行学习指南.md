# OpenCode Continuous Learning 源码逐行学习指南

这份文档面向希望一边读项目、一边学习 TypeScript 和 OpenCode 插件机制的读者。讲解基于 `0.4.0` 版本当前源码，重点文件是 978 行的 [`src/core.ts`](../src/core.ts)、667 行的 [`src/plugin.ts`](../src/plugin.ts) 和 302 行的 [`src/tui.ts`](../src/tui.ts)。所谓“逐行”不是把每个右花括号和空行机械地重复一遍，而是按照源文件的实际行号，把一个语句跨越的连续行作为一个语义单元解释；只含缩进、逗号、括号或闭合花括号的行，会跟它所属的表达式一起说明。这样既不会漏掉代码，也能看清“这一行为什么存在、谁会调用它、TypeScript 为什么允许这样写”。

阅读时请始终记住：这个项目没有训练模型，也没有修改模型参数。这里的 Continuous Learning 是一种外部持久化机制。稳定事实写进 Markdown Memory，用户画像写进 `USER.md`，项目事实写进项目分区，程序性知识写成 `SKILL.md`，后续会话再把这些内容读回来。整个系统可以压缩成一条调用链：OpenCode 加载插件，插件读取配置并创建 `LearningStore`，普通对话开始前注入已有知识，一轮回答结束后监听 `session.idle`，达到阈值时创建隔离复盘会话，复盘 Agent 通过受限工具调用 `LearningStore`，最后以原子写方式落盘。

## 先理解 TypeScript 在这个项目里的角色

根目录 [`package.json`](../package.json) 第 5 行声明 `"type": "module"`，所以项目使用 ECMAScript Module，也就是 `import` 和 `export`，而不是 CommonJS 的 `require` 与 `module.exports`。[`tsconfig.json`](../tsconfig.json) 第 3–10 行把目标语言设为 ES2022，模块和解析策略设为 `NodeNext`，允许源码导入路径直接写 `.ts` 后缀，打开 `strict` 严格检查，同时使用 `noEmit` 表示只检查类型、不生成 JavaScript。OpenCode 能直接加载 TypeScript，所以这里不需要单独构建产物。

你会频繁看到 `unknown` 而不是 `any`。`any` 的意思近似“关闭类型检查”，而 `unknown` 的意思是“值存在，但在运行时验证前不能相信它”。例如 `type UnknownRecord = Record<string, unknown>` 表示这是一个以字符串为键的对象，但每个值仍然未知；代码随后必须用 `typeof value === "string"`、`Array.isArray(value)` 或自定义类型守卫把类型缩小，才能安全使用。这个写法尤其适合配置文件、SDK 响应和模型工具参数，因为它们都来自模块边界之外。

`import type { Plugin }`、`type MemoryTarget` 里的 `type` 表示只导入编译期类型，运行时不会生成对应导入。`interface LearningConfig` 描述对象必须有哪些字段，但接口也只存在于编译期，所以从 JSON 读取以后仍然要执行运行时校验。`"user" | "agent"` 是字符串字面量联合，调用者只能传两个精确字符串之一。`keyof LearningConfig` 会自动得到所有配置键的联合；`Record<Key, Value>` 要求每个键都有一个值；`Partial<LearningConfig>` 暂时把所有字段变为可选，适合表示局部更新。

`async` 函数总是返回 `Promise`，`await` 会在当前异步函数内等待 Promise 完成，但不会阻塞整个 Node 事件循环。`Promise.all` 用于并发等待互不依赖的操作。`Map` 保存键到值的映射，`Set` 保存不重复成员。`?.` 是可选链，左侧为空时直接得到 `undefined`；`??` 只在左侧为 `null` 或 `undefined` 时使用右侧；`??=` 只在当前值为空时赋值。对象展开 `{ ...old, changed: true }` 会复制旧属性，再让后面的同名属性覆盖前面的值。`satisfies Plugin` 会检查表达式符合 SDK 的 `Plugin` 类型，却保留表达式自身的精确推导；它比强制断言 `as Plugin` 更容易发现错误。

## 从安装脚本走到真正的函数入口

Linux 和 macOS 的入口是 [`scripts/install.sh`](../scripts/install.sh)，Windows 的入口是 [`scripts/install.ps1`](../scripts/install.ps1)。二者不是 Continuous Learning 的业务核心，它们负责把同一套源码部署到 OpenCode 能发现的位置。真正的服务端入口来自安装后的 `~/.config/opencode/plugins/continuous-learning.ts`，真正的业务函数则来自安装后的 `~/.config/opencode/continuous-learning-plugin/plugin.ts`，也就是源码目录里的 `src/plugin.ts`。

### `scripts/install.sh` 第 1–84 行

第 1 行 `#!/usr/bin/env bash` 要求系统通过 `PATH` 找到 Bash。第 2 行 `set -euo pipefail` 同时开启三项保护：某条未处理命令失败就退出，读取未定义变量就报错，管道中任意环节失败都算失败。第 4 行通过 `${BASH_SOURCE[0]}` 得到脚本自身位置，`dirname` 取得 `scripts` 目录，向上一级后 `pwd` 得到绝对项目根。`$(...)` 是命令替换，`--` 表示后面的路径即使以连字符开头也不能被当成选项。

第 5 行的 `${1:-${XDG_CONFIG_HOME:-$HOME/.config}/opencode}` 有两层默认值。用户如果提供第一个参数，就把它作为目标配置目录；否则使用 `$XDG_CONFIG_HOME/opencode`；如果 `XDG_CONFIG_HOME` 也没有设置，就使用 `$HOME/.config/opencode`。第 7–13 行的 `case` 只允许目标以 `/opencode` 结尾。合法分支什么都不做，非法分支把错误写到标准错误 `>&2`，然后 `exit 1`。这是防止脚本把文件意外复制到过宽目录的第一道边界。

第 15–19 行分别计算服务端桥接目录、运行模块目录、Slash 命令目录、插件设置目录和带时间戳的备份目录。第 21 行用 `mkdir -p` 幂等创建这些目录；已存在不会报错。第 23–32 行定义 `copy_with_backup`。第 24、25 行读取函数的两个位置参数。第 26 行检查目标是否已经存在；存在时，第 27 行用 Bash 的 `${value#pattern}` 删除配置根前缀，得到用于备份的相对路径，第 28 行建立备份父目录，第 29 行以 `cp -p` 保存旧文件及其权限和时间，最后第 31 行才复制新文件。这里没有使用 Bash 的 `local`，所以 `source_path` 等变量属于脚本作用域，但后续没有命名冲突。

第 34–43 行的 `remove_with_backup` 使用同样思路处理旧文件：目标不存在就立即 `return`；存在则先复制进备份目录，再执行 `rm -f`。这个函数只用于第 52 行删除已经废弃的 `learning-mode.md`，所以删除是可恢复的。第 45–53 行是安装映射本身：桥接入口进入 `plugins/continuous-learning.ts`，`plugin.ts`、`core.ts`、`tui.ts` 进入独立运行模块目录，`plugin-package.json` 在目标处改名为 `package.json`，两个命令模板进入 `commands`，旧 Slash 命令被清理，用户手册进入设置目录。

第 55–58 行只在 `config.json` 不存在时复制默认配置，因此升级不会覆盖用户已经调整的值。第 60–62 行检查 OpenCode 配置根下能否看到插件 SDK；找不到时只输出警告，因为真实 OpenCode 安装可能用别的依赖布局。第 64–67 行用 `command -v opencode` 查找 CLI，找不到则终止。要注意，这个检查发生在文件复制之后，所以这里失败可能留下已经复制的文件，只是 TUI 尚未注册。

第 69–75 行在 CLI 改写配置前备份现有 `tui.json` 和 `tui.jsonc`。第 77 行只为这一条命令临时设置 `XDG_CONFIG_HOME`，再执行 `opencode plugin "$module_dir" --global --force`。`${config_root%/opencode}` 是删除尾部 `/opencode`；`--global` 表示注册到全局配置，`--force` 允许替换旧版本的同名本地插件。第 79–84 行只负责报告安装结果并提示完全重启 OpenCode。

### `scripts/install.ps1` 第 1–95 行

PowerShell 脚本实现相同行为。第 1–3 行 `param` 声明可覆盖的字符串参数 `$ConfigRoot`，默认通过 `$env:USERPROFILE` 拼出 `.config\opencode`。第 5 行把非终止错误提升为会被捕获或终止的错误。第 6 行使用 PowerShell 自动变量 `$PSScriptRoot` 找到项目根，第 7 行用 `Resolve-Path -LiteralPath` 获得真实绝对路径且不解释通配符，第 8 行用 .NET 的 `GetFullPath` 规范化目标路径。

第 10–12 行要求路径以 `.config/opencode` 结束，否则 `throw`。第 14–18 行用 `Join-Path` 构造各目标目录和时间戳备份目录，第 20 行批量创建，`| Out-Null` 丢弃 `New-Item` 返回的对象。第 22–31 行定义一个数组，每个内层数组都是“源、目标”二元组。第 33–43 行逐组复制：目标存在则先计算相对路径并备份，再用 `-Force` 覆盖。第 45–52 行备份并删除旧 `learning-mode.md`，第 54–57 行只在首装时复制配置，第 59–67 行分别进行 SDK 警告和 CLI 必需检查。

第 69–76 行备份 TUI 配置。第 78 行保存调用前的环境变量，第 79–85 行进入 `try`，临时修改 `XDG_CONFIG_HOME`，第 81 行用调用运算符 `&` 执行找到的 OpenCode 程序，随后检查原生进程的 `$LASTEXITCODE`。第 86–88 行的 `finally` 无论 CLI 成功还是抛错都会恢复环境变量。最后第 90–95 行输出安装位置。PowerShell 里的 `-not` 是逻辑取反，`-ne` 是不等，`-LiteralPath` 表示把路径按原样解释，双引号字符串会插值变量而单引号不会。

### `install/continuous-learning.ts` 和本地插件清单

[`install/continuous-learning.ts`](../install/continuous-learning.ts) 只有 7 行。第 1–2 行注释说明部署位置。第 3 行从相邻的 `continuous-learning-plugin/plugin.ts` 导入默认导出，第 5–6 行解释为什么不能额外导出运行时值，第 7 行只执行 `export default plugin`。OpenCode 稳定加载器会把自动发现入口里的每个运行时导出看作插件函数，所以这个文件故意保持成一个纯桥接层；它没有任何学习逻辑。

[`install/plugin-package.json`](../install/plugin-package.json) 第 2–5 行声明本地包名、版本、禁止发布和 ESM 模式，第 6–8 行要求 OpenCode 不低于 1.18.15，第 9–11 行通过 `exports` 把 `./tui` 映射到 `./tui.ts`。因此服务端和 TUI 实际是两条加载链：服务端由 `plugins/continuous-learning.ts` 自动发现，TUI 由 `opencode plugin <module_dir>` 读取本地包清单后注册。

## `src/plugin.ts`：从默认导出进入业务编排

[`src/plugin.ts`](../src/plugin.ts) 是理解整个运行过程的第一站。OpenCode 启动时只调用第 162 行开始的默认导出一次，这个函数完成初始化并返回一组 Hooks；以后每次模型提示、工具调用和会话事件都进入这些 Hooks。

### 第 1–18 行：导入和边界类型

第 1 行从 Node 内置 `node:os` 导入 `homedir`。`node:` 前缀明确这是标准库，不是 npm 包。第 2 行导入路径函数：`join` 拼接路径，`resolve` 生成规范绝对路径，`relative` 和 `sep` 判断包含关系，`parse` 取得文件系统根，`isAbsolute` 识别绝对路径。第 4 行从 OpenCode SDK 导入纯类型 `Plugin` 和运行时工厂 `tool`。第 6–16 行从 `core.ts` 导入存储类、配置函数、复盘统计函数和两个纯类型。第 18 行把 `Record<string, unknown>` 命名为 `UnknownRecord`，后续所有不可信对象先经过运行时判断。

### 第 20–160 行：把不可信输入变成业务可用数据

第 20–23 行的 `optionPath` 用动态键从插件 options 读取路径，只有非空字符串才生效，否则返回默认值。第 25–28 行的 `requireText` 处理“Schema 中可选、某个动作中必填”的参数。可选链 `value?.trim()` 在没有值时得到 `undefined`，取反后抛错；返回时再次 `trim()`，所以调用方从这里以后拿到的一定是非空字符串。

第 30–37 行的 `errorText(error: unknown)` 把任意异常转换为文字。真正的 `Error` 读取 `message`；普通对象优先 `JSON.stringify`；如果对象有循环引用导致序列化失败，则退回 `String(error)`。第 39–48 行导出 `selectProjectRoot`。第 40 行把当前目录规范化；第 41 行在没有 worktree 时直接使用当前目录；第 42–46 行计算候选 worktree 到当前目录的相对关系，既处理相同目录，也排除 `..` 开头和 Windows 跨盘符产生的绝对关系；第 47 行还拒绝把 `/` 或盘符根当作项目。因此项目 Memory 最终绑定到“包含当前目录的非根 worktree”，否则绑定当前工作目录。

第 50–56 行的 `responseData<T>` 是泛型响应解包器。`<T>` 允许每个调用点告诉编译器期望的 `data` 类型。第 51 行拒绝空值和非对象，第 52 行只断言 SDK 的最小 `{ data?, error? }` 形状，第 53 行处理错误，第 54 行只拒绝 `undefined`，所以 `false`、`0`、空数组仍是有效响应，第 55 行返回 `T`。泛型不会进行运行时深层校验，它只是统一 SDK 边界并让调用处拥有明确类型。

第 58–97 行的 `extractTranscript` 把 OpenCode 原始消息清洗成 `TranscriptItem[]`。第 59 行建立结果数组，第 60–66 行遍历未知消息并只接受带字符串 ID 的 user/assistant 消息。第 67 行把非法 `parts` 降级为空数组。第 68–79 行提取文本：第一个 `filter` 不只是过滤对象，还使用 `(part): part is UnknownRecord` 这个类型谓词告诉 TypeScript 后续可以索引；第二个 `filter` 排除合成文本和忽略文本，只保留字符串；随后 `map`、`join("\n")`、`trim` 合并正文。第 80–93 行提取工具调用，只接受 `type === "tool"` 且工具名为字符串的 part，再从 state 读取状态、输入以及成功输出或错误文本。第 94 行将统一结构推入数组，第 96 行返回。

第 99–123 行的 `lastUserSettings` 从后向前找到最近用户消息。第 99–102 行直接在函数签名中声明返回结构；第 103 行倒序循环；第 108 行安全读取 agent；第 109–119 行确认 model 是对象且 providerID、modelID 都是字符串后才构造强类型模型。第 120 行找到后立即返回，第 122 行没有用户消息则返回空对象。当前自动复盘实际只使用 `model`，`agent` 是保留信息。

第 125–134 行的 `lastAssistantSucceeded` 也倒序查找，找到最近 assistant 后用 `!info.error` 判断是否成功；找不到则返回 false。第 136–160 行的 `buildReviewPrompt` 接受 Memory 是否到期、Skill 是否到期、项目根和裁剪后的转录。第 142–159 行把规则组成字符串数组再用换行连接。两个条件表达式根据本轮阈值明确允许或禁止相应写入，项目路径通过 `JSON.stringify` 加引号，最后用 `<completed-transcript>` 边界包住已经完成的对话。

### 第 162–266 行：插件初始化、共享状态和热重载

第 162 行是默认导出：`async ({ client, directory, worktree }, rawOptions) => { ... }`。第一个参数从 SDK `PluginInput` 解构出客户端、当前目录和 worktree，第二个参数是插件配置。文件末尾的 `satisfies Plugin` 会检查整段函数确实返回合法 Hooks。第 163 行把空 options 降级为对象；第 164–172 行计算默认配置目录、数据目录、配置文件、Skills 根；第 173 行选择项目根；第 174 行读取磁盘配置；第 175 行用 `{ ...fileConfig, ...options }` 合并，后出现的 options 优先；第 176 行创建 `LearningStore`；第 177 行建立并检查目录布局。

第 179 行的 `systemSnapshots` 是 `Map<string, Promise<string>>`，按会话缓存的不是最终字符串，而是正在构建或已经完成的 Promise。这样两个并发提示钩子不会重复读取磁盘。第 180 行的 `automaticSessions` 把后台会话 ID 映射到本轮 Memory/Skill 写权限。第 181 行的 `ignoredReviewSessions` 防止复盘子会话自己的 idle 再触发复盘。第 182 行的 `reviewsInFlight` 对源会话去重并提供进程内并发计数。第 183 行的 `reviewWrites` 保存后台写入摘要，用于通知用户。

第 185–192 行定义非关键日志函数。`level` 只能是四个字符串之一。第 186 行在 Promise 前写 `void`，表示有意不等待；最后吞掉日志 API 的失败，保证日志系统不能破坏插件主流程。第 194 行把当前配置序列化成签名。第 195–208 行的 `refreshConfig` 每次从磁盘重读、合并 options、归一化并比较签名。没有变化返回 false；变化时第 199 行执行 `Object.assign(config, next)`，这是一个关键设计：`LearningStore` 保存的是同一个 config 对象引用，原地修改能让它立即看到新容量限制。如果改成 `config = next`，store 会继续引用旧对象。第 201 行清空会话快照，第 202–206 行记录开关变化。

第 210–221 行定义通知函数。通知开关关闭时立即返回；否则调用 TUI toast，并吞掉无 TUI 环境中的失败。第 223–227 行的 `requireEnabled` 是总开关守卫。第 229–236 行的 `modeState(changed = false)` 展示默认参数和派生值，`automaticReviewActive` 只有在总开关与自动复盘都开启时才为 true。第 238–243 行只为自动会话记录写入摘要。第 245–265 行的 `askForForegroundWrite` 使用 TypeScript 结构类型，只声明 context 中真正需要的字段。后台会话或关闭确认开关时直接返回，前台写入则通过 `context.ask` 请求 `continuous_learning_write` 权限。读操作不经过这里。

### 第 267–421 行：自动复盘从哪里开始

第 267 行定义闭包 `maybeAutoReview(sessionID)`。第 268–277 行是快速守卫：总开关、自动复盘、后台会话、忽略集合、同源会话正在复盘和全局并发上限，任一不满足就返回。并发满时没有排队，本次 idle 被跳过，要等该会话之后再出现 idle。第 278 行先把源会话加入 in-flight，避免后续 `await` 期间重复进入；第 279 行预留子会话 ID；第 280 行进入 `try`。

## 用三次完整调用把所有文件串起来

当普通用户发送消息时，OpenCode 已经在启动阶段调用 `plugin.ts` 默认导出，插件已经执行 `loadConfig → normalizeConfig → new LearningStore → ensureLayout` 并返回 Hooks。模型准备生成回答时进入 `experimental.chat.system.transform`，它执行 `refreshConfig`，再按 sessionID 查快照。缓存未命中时调用 `LearningStore.buildSystemSnapshot`，后者并发执行 `readMemory → parseMemory` 和 `listSkills → parseSkillHeader → trustedProvenance`，把结果追加到 system prompt。这个调用没有写入，当前会话的 Promise 快照会一直复用。

当 Agent 调用 `learning_memory add` 时，SDK 先按 Zod Schema 解析 args，然后 execute 热更新配置、检查总开关、识别是否后台会话、必要时通过 `context.ask` 请求权限，接着进入 `LearningStore.addMemory`。存储层执行 `assertSafePersistentText → normalizeOneLine → withStorageLock → readMemory → parseMemory → writeMemory → renderMemory → atomicWriteText`。任何一步失败都会阻止覆盖；成功时 rename 把完整临时文件替换为目标。

当一轮回答完成时，OpenCode 发出 `session.idle`。event hook 热更新后后台启动 `maybeAutoReview`。它依次执行 `session.messages → lastAssistantSucceeded → extractTranscript → countTranscript → getCheckpoint → isReviewDue`。达到阈值后先记录 attempt，调用 `renderTranscript`，创建 parent 子会话，取得全部工具并默认关闭，只开启三个学习工具，再把 `buildReviewPrompt` 发给隐藏 Reviewer。Reviewer 的写入重新经过上面同一套工具和 `LearningStore`，而不是绕过安全层。模型完整完成后源检查点才推进，最后子会话按配置删除。

当用户打开 `/learning-settings` 时，走的是另一条 TUI 链：命令 `run → showPanel → loadConfig → panelOptions → DialogSelect`。布尔项执行 `saveField → updateConfig → validateConfigValue → atomicWriteText`；整数项先经过 Prompt 正则和范围校验；恢复默认执行 `resetConfig → updateConfig`。服务端没有收到进程内消息，但下一次 transform、idle 或工具执行会调用 `refreshConfig`，用 `Object.assign` 原地更新 store 共用的配置对象。

## 阅读这套实现时最值得留意的设计取舍

配置有两种不同姿态：从磁盘启动时使用 `normalizeConfig` 宽松容错，用户主动设置时使用 `validateConfigValue` 严格拒绝。`readonly config` 只禁止替换属性引用，不会深冻结对象，所以热更新可以原地生效。Memory 的项目作用域来自规范化绝对路径和哈希，而不是只看目录名。系统快照缓存 Promise，使并发提示共享同一次读取，并让当前会话知识边界稳定。Skill provenance 的哈希是一种完整性和所有权保护，不是面对拥有本机写权限攻击者的密码学身份系统；它的目标是可靠识别人工作改动并让后台立即失去覆盖权。

写锁是一把跨本插件进程的粗粒度文件锁，保证更新不丢失，但没有陈旧锁回收。原子写保护文件内容完整，但没有同步父目录，因此不能承诺突然断电下的绝对持久化。Memory 字符上限按 JavaScript `string.length` 计算，即 UTF-16 code unit，而不是磁盘字节。自动复盘并发满时没有队列，只能等待下一次 idle。若 Reviewer 已经完成写入而总开关恰在最后检查前关闭，检查点不会推进，未来可能重复复盘；Memory add 的去重缓解重复事实，但复杂 Skill 更新仍需依赖模型和所有权规则保持幂等。

学完这份代码以后，可以尝试不改功能地做三个练习：先给 `loadConfig` 的坏 JSON 和 ENOENT 写独立测试，理解宽松读取的边界；再为 `isReviewDue` 写一个带失败冷却时间的纯函数测试，理解时间参数可注入为何有利于测试；最后考虑怎样在锁文件中加入安全的陈旧锁回收，同时避免误删另一个进程刚刚取得的新锁。做这些练习时继续坚持本项目的原则：外部数据先以 unknown 接收，运行时校验后再收窄；用户文件不认识就拒绝覆盖；真正的安全边界放在存储层，而不是只写在 Prompt 里。
